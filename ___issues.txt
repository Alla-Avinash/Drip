Refactor: modular split for the app (separate .d.txt vs .d.md parsing/ingest, shared core)

	Format front-ends (kept separate on purpose)
		- DripNote (the .d.txt side)
			- DripNote Parser      -> turns .d.txt text into a structured note (header, headings, tags, relations, metadata)
			- DripNote Identity    -> owns the .d.txt-style identity (@fN:hM lines + hashes) and its reconcile
			- DripNote Editor Services -> coloring, completion, diagnostics, document symbols for .d.txt only
			- DripNote Ingest      -> the .d.txt sync driver (open / save / close / delete)
		- MarkdownNote (the .d.md side)
			- MarkdownNote Parser  -> turns .d.md text into the SAME structured shape, reading its two hidden comment blocks
			- MarkdownNote Identity -> owns the .d.md-style identity (hidden <!-- drip-file --> / <!-- drip hN --> comments) + reconcile
			- MarkdownNote Editor  -> the WYSIWYG webview (chips, pickers, dropdowns) - its own editing UI
			- MarkdownNote Ingest  -> the .d.md sync driver (single-writer, reconcile-on-save rules)

	The bridge (the reuse point)
		- Note Normalizer
			- the single shared intermediate format both parsers output to, so nothing downstream cares which file it came from
			- owns the rule of what a "note" is (file identity + headings + tags + relations + metadata)

	Shared core (format-agnostic)
		- Note Index         -> SQLite write/read layer (headings, tags, relations, metadata rows, schema, id allocator); only reads the normalized shape
		- Metadata Schema    -> single source of truth for metadata types + relations (enum/datetime/duration); both formats read it
		- Tag Graph          -> tag storage + the rule for which graph is authoritative per note path (project vs KB)
		- Embeddings         -> vector encoding + search (works purely off index rows)
		- Search & Query     -> index readers: heading search, retriever queries, project/feature/issue views
		- Shared Utilities   -> file-type matching, slugging, edit guards, tiny stateless helpers

	Features (consumers - read the index, never raw file text)
		- Projects & Issues  -> projects -> features -> issues, inbox/mailbox, issue moves, sub-issue parent links
		- References & Links -> cross-note links, backlinks, link rewrite on file-id change
		- Capture            -> quick-capture + deciding where a captured note lands
		- Navigation         -> sidebar (KB tree, recents, daily notes, drafts)
		- Retriever          -> search/browse UI on top of Search & Query
		- Settings           -> metadata config, colors, file extensions, import/export
		- AI Integrations    -> LLM chat, memory, local MCP server

	Wiring (one place only)
		- Extension Activation -> only connects commands/providers/webviews; no behavior lives here

	The rule that keeps it clean
		- parsing + identity = per-format (the only thing that's different)
		- normalizing = one bridge module
		- indexing, tags, metadata, embeddings, search = shared, format-blind
		- features = read the index, never the raw file
