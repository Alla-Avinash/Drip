    How the Editor Handles File Edits and Autosave
        In-Memory Editing:
            When you open a file in VS Code, the content is loaded into memory. 
            This means that all edits you make happen in the editor's memory, not directly on the disk. 
            This allows for super-fast editing because you're not constantly reading or writing to the disk.
            It uses a data structure called a "Text Model" to keep track of changes, handle undo/redo operations, and manage cursor positions.
            The editor never writes directly to disk while you're typing. All changes are staged in memory.
            All edits are kept in memory until you hit save or autosave kicks in.
        Autosave Process:
            VS Code tracks changes in memory. It uses a "dirty" flag to know if the file has been changed and needs saving.
            When autosave is triggered (either after a delay or when the editor loses focus), the editor sends a save request to the main process.
            The main process, through the FileService, writes the changes to the disk. This means the actual write operation is done in the main process, ensuring security and consistency.

    How File Saving Works on Disk
        When you modify a file, the changes are kept in memory, and then, when you save, the following happens:
        File System Management: 
            The operating system manages where the file data is stored on the disk. 
            It doesn't necessarily move the file to a new location each time you save. Instead, it updates the file's content in place.
        Handling Size Changes: 
            If the file size increases, the operating system allocates additional space on the disk. 
            If the file size decreases, it may release that unused space. 
            This process is managed by the file system and doesn’t require moving the entire file.
        Data Structures: 
            The file system uses structures like inodes (on Unix-like systems) and MFT (on NTFS) to keep track of file locations, sizes, and metadata. 
            The actual data is stored in blocks, and only the changed blocks are updated on disk.

    How Extensions Work Together
        Companies like SAP, workday work with extensions like design patterns 
        Isolated Extension Host:
            Extensions run in their own isolated environment called the extension host. This prevents one extension from affecting the others or the main app.
            They communicate with the main process via IPC, ensuring safe interaction with system resources.
        Coordinated Interaction:
            Multiple extensions can work together because they all follow the same communication protocols. 
            They can listen to events, modify the editor, and respond to user actions.
        Extension API: 
            Provides a set of APIs for extensions to interact with the editor, file system, and other parts of VS Code.

How the Code Flow Works When You Open a Workspace and Edit a File
    Opening a Workspace:
        The main process initializes and creates the main window.
        The renderer process loads the workspace, reading the folder structure and settings.
        It uses services to fetch the file tree and display it.
    Editing a File:
        When you open a file, the renderer asks the main process to read the file content.
        The main process uses the file system APIs to fetch the content and sends it back to the renderer.
        The editor then displays the file content.
    Auto-save:
        When you make changes, the file is marked as dirty.
        If auto-save is enabled, a timer or a focus change triggers a save.
        The renderer sends the save request to the main process.
        The main process writes the file and confirms the save.

UI Components in vscode 
    UI is divided into different parts, and each has its own dedicated component.
    Toolbar and Activity Bar:
        These are part of the workbench component. 
        The activity bar is the vertical bar on the side that contains icons for the Explorer, Search, Source Control, Run, and Extensions. 
        The toolbar at the top of the editor area also falls under the workbench.
    File Explorer:
        The file explorer is also part of the workbench. 
        It is one of the views that the workbench manages, allowing you to navigate the project files.
    Editor:
        The editor itself is a part of the workbench as well, but it's a separate component within it. 
        The editor handles all the file editing, showing the content of the files, and managing the cursor and changes.


Services and Features in VScode application/ editors 
    File Handling: Services that manage reading, writing, and watching files on your disk.
    Configuration Management: Services that load, save, and manage user settings and preferences.
    Extensions Management: Services that handle loading, running, and managing extensions.
    Workspace Management: Services that handle opening, closing, and managing different workspaces or folders.


Shared Process: Caching and Background Tasks
    The shared process is like a background worker that helps keep the app fast and efficient.
    Caching: 
        This means storing frequently accessed data in memory or a temporary file so that the app doesn’t have to repeatedly read from disk. 
        For example, caching the list of files in a workspace so the explorer is fast.
    Background Tasks: 
        These are tasks that run without interrupting the user, like checking for updates, indexing files for search, or managing extensions. 
        These tasks run in the background to keep the app responsive.


MAIN COMPONENTS of VScode

    1. Main Process and Services
        Use Case: File Management
        Service Involved: FileService
        What It Does: 
            When you open a file in VS Code, the renderer process (the UI) sends a request to the main process to read the file from disk. 
            The FileService in the main process handles this request, reads the file, and sends the content back to the renderer. 
            This ensures that the UI never directly accesses the file system, keeping it secure.
    
    2. Renderer Process and Workbench
        Use Case: Displaying the Explorer
        Component Involved: ExplorerView (part of the workbench)
        What It Does: 
            When you open a workspace, the renderer process uses the ExplorerService to fetch the directory structure. 
            The service sends a request to the main process, which reads the file system and returns the data. 
            The renderer then displays the file explorer in the UI.
    
    3. Extension Host
        Use Case: Running an Extension
        Component Involved: ExtensionHost
        What It Does: 
            When you install an extension, the extension code runs in a separate process called the extension host. 
            This isolation ensures that any bugs or security issues in an extension don’t affect the main app. 
            The extension host communicates with the main process via IPC to perform tasks like accessing the file system, making network requests, or interacting with the UI.

    4. Shared Process
        Use Case: File Indexing for Search
        File Indexer: 
            Keeps track of all the files and their contents to speed up search operations.
            This index is updated in the background so that searches are instant.
        Functionality:
            When you search for a term in VS Code, the app needs to quickly find all occurrences of that term across your workspace. 
            The shared process handles indexing files in the background, so that searches are fast. 
            It keeps a cached index of file contents and updates this index in the background.

why is vscode appilcation heavy when compared to other lightweight editors?? heavy ==> compute and memory resource consumption is high
    Biggest CPU + Memory Consumers in VS Code
    1. Editor (Monaco Editor)
        This is not a simple text box.
        It does:
            syntax highlighting (tokenization)
            code parsing
            bracket matching
            auto-completion
            linting hooks
        Every time you type:
            text is re-tokenized
            sometimes partially re-parsed
        That costs CPU.

    2. Extensions (BIGGEST reason)
        Each extension runs in:
        Extension Host (separate process)
        Real examples:
            Python extension → runs language server
            Java extension → runs JVM-based server
            ESLint → continuous linting
        These do:
            background analysis
            indexing
            autocomplete suggestions
        Multiple extensions = multiple heavy processes

    3. Language Servers (very heavy)
        Used for:
            IntelliSense
            error checking
            code navigation
        Example:
            TypeScript server
            Python LSP
        What they do:
            parse entire project
            build ASTs
            track symbols
        For large projects:
            high RAM usage
            constant CPU spikes

    4. File Watchers
        VS Code constantly tracks your files:
            detects changes
            updates explorer
            triggers rebuilds
        On large projects (1000+ files):
            many OS watchers
        memory + CPU usage

    5. Search Indexing
        When you search:
            VS Code doesn’t scan files every time
        It:
            builds indexes
            caches file data
        Background process:
            reads files
            updates index
        This consumes CPU + disk IO.

    6. Renderer (UI layer - Chromium)
        Electron = Chromium
        So you are running:
            a browser engine
            layout engine
            JS engine (V8)\
        Even idle:
            memory usage is high

    7. Multiple Processes
        VS Code runs:
            Main Process
            Renderer Process
            Extension Host
            Shared Process
            Language Servers (separate)
        Each = memory overhead

    Real Example:
        Open a large React project:
        Immediately:
            TypeScript server starts
            ESLint starts
            Prettier hooks
            file watchers activate
            extensions load
        CPU spikes even before typing anything
        Tradeoff: performance vs developer experience
        VS Code chose: better experience over minimal resource usage

search in vscode 

    VS Code uses tools like:
        ripgrep (very fast search engine)
    When you search:
        It scans files very fast on demand
    But also:
        It may cache:
        recently searched results
        file metadata (file paths, sizes)
        partial indexes (not full content always)

    Then what does “indexing” mean?
    Not this:
        store every word of every file
    More like:
        store enough structure to avoid re-reading everything blindly
    Examples:
        which files exist
        which files changed
        sometimes token info (language-specific)

    Without optimization:
        10,000 files
        each search = read all files from disk

        Disk IO = slow
        CPU spikes
        UI freezes


Caching in vscode 

    1. File Explorer
        When you open a folder, VS Code reads thousands of files
        Without cache:  
            every expand/click = disk read → slow
        With cache:
            folder structure is remembered
            instant expand in explorer

    2. Recently opened files / tabs of the workspace
        You reopen VS Code → files appear instantly
        That’s cached state of the workbench:
            file paths
            cursor positions
            scroll position

    3. Editor (undo/redo + fast typing)
        The editor keeps previous states and edit history, but not disk—memory cache
        Without cache:
            undo would be impossible
            typing would lag

    4. Syntax highlighting & parsing
        When you open a file it gets tokenized (colors, syntax hilighting for different programming language syntax)
        why do we need tokenizing (breaking into pieces)?
            keyword, variable, operator, number need to have different colors to easily identify them.
            VS Code does NOT re-tokenize the whole file every time --> instead it, only the changed lines + nearby context --> called incremental tokenization 
        why do we need parsing (understanding structure)? 
            maintain a clear structure and tells us if there is any errors with the opening or closing function scope
        Why this costs CPU?? 
            because every keystroke triggers:
                token update
                sometimes structure update
                UI repaint (colors, highlights)
        Cached so:
            scrolling doesn’t re-parse everything
            switching tabs is instant
        

    5. IntelliSense 
        Language servers cache:
            symbols (functions, variables)
            imports
            references
        So when you type:
            suggestions appear instantly
        Without cache:
            every keystroke = full project scan 

    6. Extensions data
        Extensions cache:
            results
            API responses
            analysis
        Example:
            ESLint caches previous lint results
            Git extension caches repo state

    8. File watchers optimization
        Instead of re-reading everything, VS Code tracks only changed files
        Cache = “what already exists”

    9. Search
        recent results are cached 
        file paths
        partial indexing
