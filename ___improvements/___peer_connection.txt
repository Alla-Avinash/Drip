What you're describing is a peer-to-peer issue-tracking system built around local Markdown or text files, with a workflow similar to Linear, rather than a continuously connected collaboration session.

The key design change is to move from sharing a workspace to exchanging discrete, versioned operations. For example, one person creates an issue, sends it to another peer, and the other person can accept, update, or close it without both people being online simultaneously.

The repository you linked, P2P Live Share, is a reasonable starting point because it already supports peer-to-peer communication through WebRTC. However, its main purpose is real-time collaboration, including synchronized editing and workspace files. It uses Trystero with public signaling options by default, so it isn't entirely free of centralized infrastructure today.

3. How atomic operations should work
Instead of continuously synchronizing document edits, generate discrete operations.

Operation

Example

Create issue

issue.create

Change status

issue.status.set

Assign issue

issue.assignee.set

Add comment

issue.comment.add

Close issue

issue.close

Every operation should have a unique ID, target issue ID, author/peer ID, timestamp, and causal metadata such as its parent operation or version.

Example:

{
  "opId": "op_a102",
  "type": "issue.status.set",
  "issueId": "iss_8f31a2",
  "value": "in_progress",
  "author": "peer_a",
  "baseVersion": 1
}

When Peer A changes the status, the extension:

Validates the operation.

Saves it locally and updates the issue.

Queues it for synchronization.

Sends it to Peer B when a connection is available.

Lets Peer B validate and apply it exactly once logically, even if it receives the same operation multiple times.

Important: atomicity means an operation is applied completely or not at all. Use a local transaction for the operation log and materialized issue state. Network delivery itself cannot guarantee exactly-once execution, so use unique operation IDs and idempotent processing.

5. The main architecture decision
There is one unavoidable trade-off: fully decentralized does not mean automatically discoverable.

No central application server: achievable. Store issues and operation history on peers.

No always-on connection: achievable. Queue operations until peers reconnect.

No centralized signaling server whatsoever: possible, but discovery and NAT traversal become harder. You may need manual connection details, LAN discovery, or another decentralized discovery mechanism.

Conflict resolution: necessary when two peers independently change the same field while offline.

For an initial version, I would use local issue files, an append-only operation log, peer-to-peer synchronization on demand, and deterministic conflict rules. Keep the issue state separate from the transport implementation.

1. What happens when someone goes offline?
Linear documents this behavior explicitly: changes that cannot reach the backend are stored locally and retried when connectivity returns. Offline mode is a fallback, not a fully independent collaboration system. 

Linear Docs

Let's use your exact scenario:

10:00 AM — Peer A goes offline

A has a local copy of the workspace and creates issue ISS-101. The change is saved locally but cannot reach Linear's server.

10:05 AM — Peer B stays online

B creates ISS-102. The server processes and stores the issue, and other connected clients receive the update.

10:30 AM — Peer A reconnects

A sends its queued changes and retrieves the changes it missed. Its local database catches up with the shared workspace.

The important detail is that A's issue and B's issue are separate creations. A's offline issue does not disappear simply because B created another issue first.

2. How does Linear know what A missed?
Linear uses delta synchronization. Each client tracks a checkpoint representing the last synchronization action it applied. When A reconnects, it sends that checkpoint and receives the relevant changes after it, rather than downloading the entire workspace again. Linear documents an ordered, append-only log of synchronization actions for each workspace. 

Linear

For example:

Shared workspace change log (simplified)

501
issue.create — ISS-102 by B

502
issue.update — existing issue by B

503
issue.create — ISS-103 by B

A's last checkpoint: 500

On reconnect: A fetches applicable actions 501–503, applies them locally, and advances its checkpoint.

This log is a conceptual illustration, not Linear's actual production records.

3. What if A and B modify the same issue?
This is the more difficult case. Linear's documentation warns that offline edits can overwrite another person's changes: it does not simply reject an offline change because it was created earlier. 

Linear Docs

For example:

Time

Peer A (offline)

Peer B (online)

10:00

Sees status Open

Sees status Open

10:05

Changes description

Changes status to In Progress

10:30

Reconnects and submits its pending edit

B's change is already on the server

If A only changed the description, the changes concern different fields. But Linear's documented offline behavior means you should not assume every conflicting edit will be merged intelligently. If both change the same field, an overwrite is possible.

4. What this means for your decentralized extension
You can adopt Linear's strongest synchronization idea without adopting its centralized backend:

Give every operation a unique ID.

Maintain a local append-only operation log.

Track the last operation each peer has received from other peers.

Exchange only missing operations when peers reconnect.

Define explicit conflict rules for simultaneous edits.

The key difference is authority: Linear has a central server that maintains the authoritative workspace state. Your system has no such server, so peers must agree on how to reconcile competing operations.

My recommendation: model your extension as a local-first, operation-based system with durable logs and explicit conflict handling. Use P2P only to exchange operations, not as the source of truth. That is the architectural direction closest to Linear's synchronization model while preserving your decentralized requirement.

2. How is a connection established?
The repository supports more than one connection mode. The invitation link identifies which mode to use, along with the room and host information. This is implemented in src/sync/share.ts. 

GitHub

Mode A: Trystero (MQTT or Nostr)

Peers join the same room using a signaling strategy. That strategy helps them discover one another and exchange WebRTC connection information. Once WebRTC is established, collaboration data travels directly between peers.

Source: Trystero connection implementation · How Trystero works

Mode B: WebSocket relay

The host or guest connects to a WebSocket server. In this mode, the server routes messages between participants instead of using a direct WebRTC data channel for the collaboration transport.

Source: src/sync/ws/guest.ts and src/sync/ws/host.ts

Mode C: Host Locally

The host listens on a selected local network interface and guests connect directly to it. This avoids a separate relay server when the network permits direct connectivity.

Source: Repository README

What happens in WebRTC mode?
Host starts a session. The extension generates a room ID and connection configuration.

Host shares an invitation link. The link encodes the connection type, room ID, and signaling endpoint or host address.

Guest joins the room. Trystero discovers the other peer and exchanges the information needed to establish a connection.

WebRTC negotiates the connection. The peers establish a direct data channel if network conditions permit.

The extension initializes collaboration. The guest waits for an init message from the host, receives a Yjs document update and host metadata, then installs the filesystem, RPC, terminal, and other handlers.

The final step is directly visible in createGuestSession() and createHostSession(). A guest waits up to 15 seconds before displaying a warning that no host was found, with an option to continue waiting.

4. What happens when a connection breaks in the middle?
This is where the source code becomes especially relevant to your project.

There are three distinct mechanisms to understand: message retransmission, peer-disconnection detection, and session reconnection.

A. Message retransmission and acknowledgements
In src/sync/trystero/controller.ts, the extension implements a lightweight reliability layer over Trystero's message transport.

The important constants are:

ResendTimeout = 2000: a message still awaiting acknowledgement becomes eligible for retransmission after two seconds.

AckInterval = 200: acknowledgement processing is throttled to roughly a 200 ms interval.

For ordinary messages, the controller assigns a per-peer sequence number, keeps a pending-send record, and retransmits messages that haven't been acknowledged. The receiver buffers out-of-order messages and applies them in sequence. 

GitHub

Example: a message is lost or delayed

Host

Sends message #7

Guest

Message not received

After the retransmission timeout, the controller sends message #7 again.

Host

Resends #7

Guest

Receives and applies #7

Simplified illustration of the controller's retransmission mechanism.

There is an important limitation: this is in-memory delivery tracking, not a durable offline queue. The controller removes a peer's state when that peer disappears from the active peer list. If a peer disconnects for a long time, the sender cannot rely on this pending-message map to preserve and replay all missed changes after a fresh session is established. 

GitHub

Also, the controller's acknowledgement confirms receipt and ordered processing at the message layer; it is not a durable disk commit acknowledgement.

B. Detecting a broken connection
In src/sync/connection.ts, the extension subscribes to the connection's onClose event. When that event fires, it invokes onSessionClosed() and displays a dialog explaining that the connection may have closed because of network issues or a relay server going offline. 

GitHub

The guest session also watches whether the host remains in the active peer list. If the host disappears, it invokes the same session-closure flow. 

GitHub

C. Reconnecting
The function onSessionClosed() in src/session/index.ts does the following:

Saves the current connection configuration in memory.

Clears the active session, disposing its scope.

Shows an error dialog with a Reconnect option.

If the user selects Reconnect, waits 500 ms.

Calls createGuestSession(config) or createHostSession(config), depending on the former role. 

GitHub

That means the repository's documented source behavior is user-prompted session recreation, not a general-purpose automatic offline synchronization protocol.

There is an important nuance: recreating a guest session runs the initialization handshake again. The guest waits for the host's init message, and the host sends its current Yjs document state when a peer joins. This restores initial shared-document state, but does not establish that all unsaved offline edits from the old session will be merged or replayed.

6. What should you take from this for your own extension?
The useful parts to reuse are the connection abstraction, message routing, peer tracking, and transport-level acknowledgement logic. The parts you should build separately are durable operation storage, missed-operation exchange, and conflict resolution.

For your issue tracker, I would design this sequence:

1. Create operation locally

Write issue change to a durable local log

2. Exchange operations with peers

Use P2P transport when a connection is available

3. Track acknowledgement and checkpoints

Know which operations each peer has received

4. Reconnect and request missing operations

Compare known operation IDs and exchange the gaps

5. Validate and apply idempotently

Deduplicate operations and resolve conflicting changes

The architectural lesson is simple: a reliable connection and reliable synchronization are two different problems. P2P Live Share addresses real-time transport and collaboration. Your project needs to add durable, offline-first synchronization above that transport layer.
