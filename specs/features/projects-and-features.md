# Feature: Projects and features

## What it is

Work is organized into **projects**, and each project is broken into **features**. This mirrors Linear's project structure and is the backbone for planning and tracking.

## How to access it

- Create, open, rename, and delete projects from the **Projects** sidebar section (above Knowledge Base). Deleting a project removes the folder and its rows from both local indexes, so it leaves the Project View list and the Settings project dropdowns. Shared projects that are sharing-on show a green online count on the folder. That count updates every 30 seconds (or when someone joins, leaves, or sharing is started or stopped). The Projects list does not keep reloading in the background.
- Browse them in the **Project View** panel (via the **Open Project View** command). The project list also has **Join new Project**.
- The Knowledge Base tree does not hold or create `.p` folders.

## Where projects live

Every project folder sits inside one special folder at the knowledge-base root: **`.drip.project`**. That folder is created when a knowledge base is selected. It is hidden from the Knowledge Base tree (same idea as `dailynotes.drip`) and is the only home for `.p` folders.

`.drip.project` is not the `projects.drip` SQLite index. The folder is the files; the SQLite file is the derived project index.

The **Projects** sidebar is the Knowledge Base tree scoped to `.drip.project`: same open / rename / delete / New / drag. **New** here is New Project, New Feature, New Note, **Join project**, and **Import project**. A project’s context menu can **Export this project** (the whole `.p` folder, including `_concepts`, `_decisions`, `_archive`, and the `.drip/` sidecar — even when those special folders are empty) so it can be moved to another disk or another knowledge base.

A `.p` folder may only be created directly under `.drip.project`.

## Structure

- A **project** is a folder with a project index note (`.project` file-level type). It carries status, priority, and deadline.
- A **feature** is a folder (or file) with a feature index note (`.feature` file-level type). It carries a `category` (enum).
- The project/feature index note is created in the KB's default new-note format: `_<Name>.p.d.txt` / `_<Name>.f.d.txt`, or `_<Name>.p.d.md` / `_<Name>.f.d.md` when the default is `.d.md`. In a `.d.txt` index the h0 heading carries the type marker (`# .p Name` / `# .f Name`); in a `.d.md` index the type is recorded in the h0 hidden comment (`<!-- drip h0 | project -->` / `<!-- drip h0 | feature -->`).
- Both projects and features get stable entity IDs (`f-N` for features; the folder acts as the project container). A project that has been shared with other people also has a hidden **project id** that survives folder renames — the folder name is not the identity. Features carry a hidden unique id as well as `f-N`; if two people mint the same `f-N` offline, the later one is reminted (see Project sync).
- A project folder may contain a `.drip/` sidecar (project id, members, tags, metadata overrides, operation log, and the project's own `@fN` file-id high water). That sidecar is part of the project, not of the knowledge-base index. A solo project may get a sidecar just to remember its file-id sequence; sharing adds the rest. Notes created inside the project use that sequence (`@f0`, `@f1`, …), not the knowledge-base file-id pool. See Project sharing.
- **Concepts** and **decisions** are project-scoped entities tracked alongside features. Concepts live in the project's `_concepts` folder and get a `c-N` number; decisions live in `_decisions` and get a `d-N` number. A concept carries `status` and `domain`; a decision carries `status`, `category`, a `superseded-by` link to another decision, and a `concept` link. Issues can link to many concepts and many decisions, and a decision can link to many concepts — stored as list links, like tags.
- Creating a project also creates its special subfolders — `_concepts`, `_decisions`, and `_archive` — so they are always present and empty. Notes can be created directly inside `_concepts` and `_decisions` (a note in `_concepts` is a concept, a note in `_decisions` is a decision). Completed issues that have been done for 3 days are moved into `_archive` (see Issues). Elsewhere in a project, notes are only allowed inside feature folders.

## The Project View panel

A Linear-style panel (`drip.openProjectView`) that:

- lists projects from the index,
- lists each project's children (features, and issues not assigned to a feature),
- is backed by the index query so it reflects the current state.

The **projects list** has a toolbar (search + Filter / Display / Sort menus) and two layouts:

- **Search** filters instantly by title or path, keeping focus while typing.
- **Filter** narrows by metadata fields (status, priority, deadline presets or a custom date). Active filters show as chips under the toolbar; clicking a chip opens that field's checkbox dropdown right on the chip.
- **Display** toggles which fields are shown and switches between **List** and **Board** view.
- **Sort** groups/orders the results. List view has **Group by + Order by**; Board view has **Column + Row + Order by**, with ascending/descending (and custom order for enums) direction toggles. A field used on one axis is hidden from the others, and enum groups always show every schema value even when empty. Datetime groups bucket into quarters (e.g. `2026 Q1`).
- Each project shows its issues as a clickable **issue bubble** with a fraction `completed / total`. Clicking it opens a dropdown breaking down the issues by status. In the board view this bubble sits on the card's last line.
- Filtering and sorting are done in the webview on the already-loaded project list (no extra query).
- The toolbar is remembered while navigating: opening a project hides it (the detail view takes over), and going back restores it with the same search/filter/sort.

Inside an open project, the panel has two view modes, switched with a **Features / Issues** toggle that sits right beside the **New issue** button.

If the project has teams, a **Team** dropdown sits in that same header with three kinds of choice: **My Teams** (the default — a mix of every issue in a team this person belongs to), each individual **team**, and **None** (all issues in the project, no team filter). Features view and Issues view honor that selection. Every member sees the whole project — the team pick is a personal filter, not a permission gate, because the shared folder already carries every issue. **New issue** is hidden if this person’s role cannot create issues. Creating an issue offers an optional team pick: a creator on exactly one team has that team pre-selected, while someone on several teams (or none) starts unassigned. Leave it empty to keep the issue unassigned. **Group by team** is available in Issues view.

**Chat.** On a shared project, a single **Chat** header button opens one chat panel with the whole-group **Project talk**, a **Team talk** room for each of your teams, an **Issues** list, and a **Direct messages** list. Each channel shows a corner badge with its unread count, and the Chat button shows the total across rooms and issue chats. The **Direct messages** header has a **+** beside it; pressing it shows a search box to pick any project member, and the box dismisses when you click anywhere outside it. The direct-message list only appears once a real conversation with that person exists. A **Mentions** channel lists every message across the rooms — project talk, team talk, direct messages, and issue chats — that tagged you with `@name` or `#name` (Slack-style), split into **Unread** and **Read**; only the unread count shows on its badge, and opening it marks those read while keeping them listed below. An issue mention is titled by its issue key and opens that issue's chat when clicked. In the message box, typing `@` or `#` shows a dropdown of matching names to autocomplete, and `@`/`#` names are tinted with the theme link colour inside messages. Opening a room marks it read, and clearing a room drops its unread to zero right away. Every message shows its time, and the history is split by **day dividers** ("Today", "Yesterday", or a full date) whenever the date changes. A message you sent carries a single tick that turns into a **blue tick** once another member has read up to it (their read cursor is shared back over the network). The **Issues** section shows only the issue chats that are unread, mention you, or mention a team — each titled by its issue key (`#i-23`). In an issue chat, and only there, you can `@team-name` a whole team; that message is also copied into that team's talk room, where clicking it opens the issue's chat. Issue talk also lives under the heading form on the right when that heading is an issue — **Save to issue note** then **Clear**. Chat is not stored in the issue file; it lives as a short JSON room in the project sidecar, capped to keep it scratch.

**Private chat (DMs and team talk).** Direct messages and team talk are encrypted so only the participants can read them; project talk and issue chat stay open. Each DM room and each team room has its own random AES-256-GCM room key. A message's text and mentions are sealed with that key before it is written or broadcast, so every member still receives the ciphertext (the peer network broadcasts everything) but only key-holders can open it. The room key is handed out by sealing it to each participant's separate X25519 encryption key (the signing key only signs, it cannot encrypt). Each member's encryption public key travels on their **hello** when peers reconnect, and is backfilled onto their member record, so a later message can always seal the room key to them; the sealed copies themselves travel with the next message, and a peer opens only the copy addressed to it and keeps it in **Secret Storage** — the same OS-encrypted, login-protected vault that holds the private identity keys — never in the synced sidecar. Each room keeps a short **history of key generations** rather than a single key, and every message records which generation sealed it: a new generation is minted whenever the participant set changes (a member removed from a team loses future messages, a newly added member receives the key on the next message), and a current member simply opens older messages with the generation each one names, so history stays readable. Generations that no stored message references are swept away automatically on each rotation and whenever a room is cleared, so dead padlocks are not hoarded. The honest limit: a removed member keeps the copy they already received — nothing can un-send it.

**Every message is individually signed.** Each message carries its author's Ed25519 signature over the whole message (or its sealed bytes), so any peer can tell a line was not forged, rewritten, or swapped — even after the recent operation log that carried it has been folded away. On read, messages that fail their signature (or whose author is unknown) are dropped, and the room file is the durable record (a hand-edited line self-heals once a re-sync or a fresh folder snapshot restores it). Legacy messages from before this signing existed are kept as-is. Read receipts are small signed operations: when you open a room, your new read position is shared, so other members can show the blue tick.

In the detail header, a **Settings** (gear) icon sits to the left of **Overview** and **Tags**, which sit to the left of the Features/Issues toggle. The gear offers two choices: **Project metadata** (DRIP Settings → Project Metadata with that project pre-selected) or **Share settings** (DRIP Settings → Project Sharing for that same project). Once shared, the header shows the members and a small sync status. **Overview** opens the project's index note `_<Name>.p.d.txt` (or `_<Name>.p.d.md` when the default new-note format is `.d.md`), creating it first if missing. **Tags** opens a popover listing the project's own tags (see "Per-project tags"): each tag can be renamed, given a description, or deleted with inline controls, and new tags can be added there.

Each feature row also has an **Overview** button on its right, which opens that feature's index note — `_<Name>.f.d.txt` (or `_<Name>.f.d.md` when the default new-note format is `.d.md`) for a `.f` folder (created if missing), or the feature file itself for a standalone `Name.f.d.txt`. Both folder features and standalone `.f.d.txt` feature files appear in the Features section with their issues, so file-format features are listed and grouped exactly like folder features.

- **Features view (default)** keeps the original grouped layout. A **search bar** filters the project's issues by title or issue key, keeping results grouped into the existing **Project issues (_issues)** and **Features** sections. Empty sections (and empty features) are hidden while searching, and a "no issues match" note shows when nothing matches. Issues always render as a **file tree** with connected guide lines (`├─` / `└─` / `│`): each issue joins to its parent with a branch or corner line, and vertical lines run through ancestor levels so the whole hierarchy reads as one continuous tree. The lines are drawn with CSS borders rather than spaced monospace characters, so they stay tight and connected; they are tinted from the theme foreground at partial opacity, so they read light on dark themes and dark on light themes. Top-level rows are flush with no leading connector — the connector appears only on nested rows. Issues whose parent lives in the same section (the same feature or inbox) sit under that parent. A **Show repeated parent issue** toggle next to the search bar additionally reveals, as dimmed rows, the missing ancestors of an issue whose `parent:` link points to an issue in a *different* feature or file (so the full cross-section chain is visible); when off, those issues simply appear as top-level rows.
- **Issues view** gives the project's issues the same search/filter/display/sort toolbar the projects list has: a search box plus **Filter**, **Display**, and **Sort** menus with **List** and **Board** layouts, Group by / Column / Row / Order by, and ascending/descending direction. **Feature** is an issue field (the feature each issue belongs to, or "Project issues" for inbox issues, or "Other"), so it can be used to group, column, row, filter, or sort. Issue rows/cards open the issue's heading on click; the Assign/Move/Sub actions stay in the Features view.

Each issue row carries two small actions (hidden when this person’s role cannot do them):

- **Assign** (project inbox issues) and **Move** (feature issues) both open the **RHS Storage sidebar in "move issue" mode** for that issue.
- **Sub** opens an inline input directly under the issue to create a sub-issue there, instead of a top-level prompt.

**Move-issue mode (RHS Storage).** Reuses the Storage sidebar with a project-scoped overlay, so the normal Storage flow is left untouched. The header shows the project name and the full title of the issue being moved (not truncated). The **Cancel** and **Move** buttons sit together at the bottom, with **Move** disabled until a destination is chosen. When it opens:

- **Suggestions / AI / Browse** buttons drive a project-scoped browser that mirrors the Storage picker's format. **Browse** shows the project's features first (highlighted with an accent border), followed by the project inbox, then drills down: selecting a feature shows its folders/files, and selecting a file shows the note's full heading tree. **Suggestions / AI** rank by the stored embeddings (heading vectors for issues, folder vectors for features) with a word-match fallback; in ranked mode only the **top 4 features** show their embedding score, and everything else (remaining features, the inbox, project issues) shows no score. From a ranked list the user can still drill into a feature/file to choose the exact landing spot (mailbox or a specific heading).
- A feature folder's file list hides the two housekeeping notes — its mailbox `_inbox.d.txt` and its index note `_Name.f.d.txt` / `_Name.f.d.md` — because picking the feature directly already routes to the mailbox.
- The heading tree shown for a file includes both **persistent** (`# .…`) and **non-persistent** (`# …`) headings, exactly like the Storage heading tree, with a "Persistent only" toggle that hides non-persistent headings and promotes their children. Headings are **collapsible** (a chevron folds/unfolds their children) and are shown **as-is** with their `#` prefix — an issue heading reads `# .i-N …` with no special icon, so nothing is pre-selected when a file opens.
- A feature can be picked directly (its "Inbox" action) to put the issue in that feature's mailbox (`_inbox.d.txt`); the feature's own row reads **"feature name (inbox)"**. The project root also offers **"Move to project inbox"** (quick) and a **"Project issues"** drill-down that lists the project's inbox issues as a tree so the issue can be nested under a specific project issue.
- Opening a file shows its heading tree with the **file name as the top "file root" row** (`📄 name`), exactly like the Storage heading tree. **Double-clicking any heading** (persistent or not) makes it the **placement anchor**: the anchor is highlighted in a bordered box and a **draggable placeholder row** (labelled with the moving issue) appears inside its children list — the same selection + drag-reorder used to ingest a note into Storage. Dragging that placeholder row up/down reorders it live among the anchor's children; on drop the slot becomes the recorded position (first child, after a sibling, or last child under the anchor). Double-clicking the **file name (file root)** instead anchors the file's top level, where the placeholder can be dragged to the **top** (before the first heading) or **bottom** (after the last heading) of the file — no hierarchy. A sub-issue (one that has a parent) cannot be nested under another issue — its existing `parent:` link would fight the new indentation — so double-clicking an issue heading shows an error asking for **Remove parent / hierarchy** to be ticked first; placing it above/below as a sibling keeps its `parent:` link intact.
- The breadcrumb reads as **project name › feature name › path inside the feature**, using clean names (no repeated feature-folder prefixes or raw file paths).
- Two checkboxes — **Persistent only** and **Remove parent / hierarchy** — sit side by side in one horizontal row above the Move button. **Remove parent / hierarchy** unchecked (default) keeps the issue's `parent:` link wherever it lands (inbox, feature mailbox, or under a plain heading); checked detaches the issue from its hierarchy — its `parent:` line is dropped — so it can be placed under any heading or issue, and its hierarchy is then whatever the new location gives it.
- The issue being moved and all of its descendants are excluded, so it can never be placed under itself.
- Nothing changes until the user clicks **Move** (the confirmation); Cancel dismisses the mode. A move is always a move — the issue is removed from its old file and added to the new location, never appended.

Moves are performed on the host: the issue block is cut from its current file, its outline parent is recorded as `parent: i-N` when it leaves a nested position (so the indentation link survives a move to the inbox or a feature mailbox), and it is appended to the destination — a feature's `_inbox.d.txt`, the project's `_issues.d.txt`, the top or bottom of a note, or relative to a heading or issue in a note (above it, below it, or under it as a child). The destination is written **before** the source, so a move that can't complete (e.g. the "has a parent" refusal, or the target heading/issue isn't found) leaves the issue untouched in its source file rather than losing it. When a subtree moves, its heading and every child lose the heading's base indent (one tab level) so the internal hierarchy is preserved relative to its new parent. The issue's `parent:` line is preserved on the way to the inbox, a feature mailbox, a plain heading, or a sibling position; it is stripped only when the issue is re-parented under another issue (indentation becomes the source of truth there) or when **Remove parent** is checked.

## Sub-features

- **Project/feature folders** — creating and watching project and feature folders. New projects are created only in the Projects section (`.drip.project`).
- **Project index** — indexing projects and their structure into `projects.drip` (a separate SQLite file from the document `index.drip`, so project headings stay out of global search).
- **Project view query** — the queries that power the Project View panel (read from `projects.drip`, with file paths resolved from the shared `files` registry in `index.drip`).
- **Convert folder to feature** — a folder can be promoted to a feature folder.
- **Per-project tags** — each project keeps its own tag graph (same node/link shape as the global tags graph, plus an optional per-tag description), separate from the global tags graph. They are managed from two places: the **Tags** popover in the Project View detail header (which lists the top-level tags with name + description) and the **Projects** mode of the Tags graph panel (full graph editing with links, groups, and sub-tags). They are stored in the project's `.drip/` sidecar so they travel with the project (including to other members). See Project sharing.
- **Project sharing / sync** — a project starts solo and can be shared with other people. Only that project folder is the shared world. See Project sharing and Project sync.

## Flow (plain steps)

1. User creates a project in the Projects section (it lands in `.drip.project`), then adds feature folders inside it.
2. The project index records the project/feature structure with entity IDs in `projects.drip`.
3. User opens the Project View to browse projects → features → issues in a Linear-style layout.
4. The project can stay solo, or be shared from Share settings so other people join it (see Project sharing). A joined or imported project also appears in the Projects section.
